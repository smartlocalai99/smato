# Driver Management Design

## Goal

Add an authenticated driver-management area to the existing Smato admin dashboard. An admin can register a driver, see every registered driver, and update a driver's personal, vehicle, licence, Aadhaar, and document details.

## Scope

The feature includes:

- Admin navigation links for the dashboard, driver list, and driver registration.
- A dedicated registration page.
- A searchable driver list.
- A dedicated edit page for each driver.
- Private storage for the driver photo, Driving Licence image, and Aadhaar image.
- Database and storage policies that only allow authenticated admins to access driver information.
- Validation, duplicate detection, responsive presentation, and clear loading, empty, success, and error states.

Deleting or deactivating drivers, keeping a change-history log, assigning multiple drivers to one auto, and public driver access are outside this version.

## Routes and Admin Shell

The authenticated admin area will use a shared shell so all admin pages have consistent access control, navigation, and sign-out behavior.

- `/admin` remains the fleet, advertisements, and team-access dashboard.
- `/admin/drivers` lists registered drivers and provides search and edit links.
- `/admin/drivers/new` contains the registration form.
- `/admin/drivers/[id]/edit` loads and updates one driver.

The shell displays links named **Dashboard**, **Drivers**, and **Register driver**. Unauthenticated visitors to any admin route see the existing mobile-number and PIN sign-in screen. Successful sign-in returns them to the requested admin route.

## Driver Data Model

Create a `drivers` table with these columns:

| Column | Type | Rules |
| --- | --- | --- |
| `id` | `uuid` | Primary key, generated by PostgreSQL |
| `name` | `text` | Required |
| `mobile` | `text` | Required, unique, normalized to 10 digits |
| `auto_number_plate` | `text` | Required, unique, normalized to uppercase without spaces |
| `driving_licence_number` | `text` | Required, unique, normalized to uppercase without spaces |
| `aadhaar_number` | `text` | Required, unique, normalized to 12 digits |
| `photo_path` | `text` | Required after registration upload finishes |
| `driving_licence_image_path` | `text` | Required after registration upload finishes |
| `aadhaar_image_path` | `text` | Required after registration upload finishes |
| `created_at` | `timestamptz` | Defaults to current time |
| `updated_at` | `timestamptz` | Defaults to current time and updates on row changes |

The unique auto-number constraint enforces the agreed rule: one auto can belong to only one registered driver. Mobile, Driving Licence, and Aadhaar are also unique so accidental duplicate registrations are rejected.

The existing `autos` table remains the tablet/fleet check-in source. Registering or changing a driver's auto number upserts the normalized plate into `autos` so it is available to the existing fleet and advertising flows. The driver row owns the one-driver-per-auto rule; deleting old `autos` rows is outside this feature because those rows may contain live tablet state.

Row-level security is enabled on `drivers`. Select, insert, update, and delete policies require `auth.role() = 'authenticated'`; the public/anonymous client cannot access personally identifiable information.

## Private Document Storage

Create a private Supabase Storage bucket named `driver-documents`. Files are stored by driver ID:

```text
<driver-id>/photo.<extension>
<driver-id>/driving-licence.<extension>
<driver-id>/aadhaar.<extension>
```

Storage select, insert, update, and delete policies require an authenticated session and the `driver-documents` bucket. The application generates short-lived signed URLs when an admin needs to display a private file. No public URLs are stored or rendered.

The driver photo accepts JPEG, PNG, or WebP. Driving Licence and Aadhaar uploads accept JPEG, PNG, or WebP. Each file is limited to 5 MB. Registration requires all three files. Editing keeps the current file unless the admin chooses a replacement.

## Registration Flow

The registration form contains:

- Driver name
- Mobile number
- Auto number plate
- Driving Licence number
- Aadhaar number
- Driver photo upload and preview
- Driving Licence image upload and preview
- Aadhaar image upload and preview

The browser normalizes and validates the entered values before making requests. Registration then:

1. Inserts the driver row with the normalized text values and temporary null file paths.
2. Uploads all three files to the new driver's folder.
3. Updates the driver row with all saved paths.
4. Upserts the auto number into `autos`.
5. Navigates to the driver list with a success message.

If a file upload or final update fails, the app removes any files uploaded during that attempt and deletes the incomplete driver row. The form remains populated and shows an actionable error. Database uniqueness errors identify the conflicting field in plain language.

## Driver List

The driver list loads all registered drivers for the authenticated admin, ordered by newest registration first. It provides a client-side search over name, mobile, auto plate, and Driving Licence number.

Each desktop row and mobile card shows:

- Signed driver-photo thumbnail
- Driver name
- Mobile number
- Auto number plate
- Masked Driving Licence number
- Aadhaar in the form `•••• •••• 1234`
- Edit link

The page has explicit loading, load-error, empty, and no-search-results states. The empty state links directly to **Register driver**. Full Aadhaar and Driving Licence values and their documents are shown only on the authenticated edit page.

## Edit Flow

The edit route loads the driver by route ID. A missing driver shows a not-found state with a link back to the driver list.

Text fields are prefilled with the current values. Existing private images are displayed through signed URLs. Selecting a replacement shows a local preview; leaving a file input empty preserves its current file.

On save, the app:

1. Validates and normalizes all text fields.
2. Uploads selected replacement images to unique temporary object names.
3. Updates the database row with changed values and replacement paths.
4. Upserts the current auto number into `autos`.
5. Removes superseded storage objects only after the database update succeeds.
6. Returns to the list with a success message.

If the database update fails, newly uploaded replacement objects are removed and the existing row and files remain intact.

## UI Direction

The feature extends the existing light, daytime admin-console palette and typography rather than introducing a separate visual language. The shared admin header becomes a compact navigation rail on wide screens and a horizontally scrollable navigation bar on narrow screens.

The distinctive element is a document-status strip in the form and driver rows: three small, functional markers for **Photo**, **DL**, and **Aadhaar** clearly communicate whether each required record is present. This reflects the real registration workflow without decorative dashboard widgets.

Forms use a disciplined two-column desktop layout and one-column mobile layout. Upload controls include previews and exact file guidance. Buttons use consistent action names: **Register driver**, **Save changes**, and **Replace image**. Keyboard focus remains visible and status messages are announced to assistive technology.

## Validation and Error Handling

- Name must be non-empty after trimming.
- Mobile must contain exactly 10 digits.
- Aadhaar must contain exactly 12 digits.
- Auto number plate and Driving Licence accept letters and numbers, normalize to uppercase without spaces, and must remain non-empty.
- All three registration files must be an allowed image type and no larger than 5 MB.
- Edit replacements follow the same file rules.
- Duplicate mobile, auto plate, Driving Licence, or Aadhaar values produce field-specific messages.
- Submit controls are disabled while a save is in progress to prevent duplicate operations.
- Unexpected database or storage failures show a retryable form-level message without discarding entered values.

## Code Boundaries

- Shared admin-authentication and navigation components own session state and shell rendering.
- Driver validation and masking helpers remain pure and independently testable.
- Driver form components own input rendering and previews but receive initial values and a submit operation from their page.
- Supabase driver helpers own database queries, signed URLs, uploads, cleanup, and duplicate-error translation.
- Route pages own loading states, navigation after successful operations, and route-specific copy.

The existing advertisement and fleet behavior must remain unchanged while the current `/admin` page moves under the shared shell.

## Testing and Verification

Automated tests cover:

- Mobile, Aadhaar, auto plate, and Driving Licence normalization.
- Required-field and file validation.
- Aadhaar and Driving Licence masking.
- Duplicate database-error mapping.

Build and browser verification cover:

- Existing admin sign-in and dashboard still load.
- Navigation links reach all driver routes.
- A valid driver with three images can be registered.
- The new driver appears in the searchable list with masked identifiers.
- Full details and protected images load on the edit page.
- Text fields and individual images can be replaced.
- Duplicate auto registration is rejected with a clear message.
- Unauthenticated access cannot read the driver table or private bucket.
- Desktop and mobile layouts remain usable.

## Deployment Requirement

After the application code is deployed, `setup.sql` must be run again in the connected Supabase project's SQL Editor. The script remains idempotent and adds the `drivers` table, indexes, timestamp trigger, private bucket, and security policies without recreating existing fleet or advertisement data.
